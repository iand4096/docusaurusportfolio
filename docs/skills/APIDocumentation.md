I have twelve years of experience creating API and SDK documentation for fintech and financial-services companies such as Morgan Stanley, Mastercard and Paysafe, supported by my software-development background.

Where practical, I build and test realistic full-stack integrations, reproduce developer workflows and validate API behaviour, or review source code before I write the documentation. This helps me identify gaps between specification and implementation and provide guidance based on practical experience with the API.

## API and SDK documentation {/* #api-and-sdk-documentation */}

<CapabilityGrid>

* **Guides and tutorials**<br />
  Conceptual guides, integration tutorials and use-case documentation built around developer tasks.

* **API reference**<br />
  REST endpoints, request and response models, and OpenAPI content for generated reference documentation.

* **SDKs and clients**<br />
  Handwritten SDKs, autogenerated language-specific clients and SDK method documentation.

* **Workflows and webhooks**<br />
  Multistep API workflows, sequence diagrams, webhooks and asynchronous processing.

* **Authentication and security**<br />
  Configuration and procedures for accessing APIs securely using authentication and encryption.

* **Errors and code examples**<br />
  Error codes, retry strategies and code examples designed around realistic integration tasks.

</CapabilityGrid>

I focus on the complete developer journey rather than documenting individual endpoints in isolation.

## Web and API security {/* #web-and-api-security */}

My annual security training covers common OWASP vulnerabilities. I have also written Python code to process certificates, encrypt and decrypt payloads, create and validate tokens, and test secure integrations in sandbox environments, including secure webhook and callback processing.

I use this experience to investigate security-sensitive API behaviour and explain authentication and cryptographic requirements in developer documentation.

## Technical investigation {/* #technical-investigation */}

I work across specifications, source code, logs, API clients and working integrations to establish what a system actually does. This is particularly useful when API behaviour is poorly documented or the original subject-matter expertise is no longer available.

## Defect investigation and release readiness {/* #defect-investigation-and-release-readiness */}

My testing experience includes black-box, component, integration and usability testing.

<CapabilityGrid variant="checklist">

* Identify and reproduce defects

* Record expected and actual behaviour, reproduction steps and evidence

* Raise and manage defects through Jira

* Work with engineers to clarify issues

* Retest fixes

* Help prioritise defects by severity and customer impact

</CapabilityGrid>

Earlier in my career, I took on dedicated QA responsibilities for a software project alongside my documentation work. I raised approximately **600 issues**, helping the team move the product towards a stable and releasable state.

## Documentation grounded in working software {/* #documentation-grounded-in-working-software */}

My development and testing experience helps me answer practical questions before publishing:

* Can a developer complete the integration using the documented steps and code examples?
* Does the implementation behave as the specification says?
* Are authentication, encryption and asynchronous workflows fully explained and testable?
* Does the documentation cover failures, troubleshooting and differences between sandbox and production behaviour?

The objective is documentation validated against real developer workflows that gives developers a reliable basis for building secure integrations.
